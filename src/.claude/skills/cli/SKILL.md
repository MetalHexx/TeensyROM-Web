# CLI Skill

Routing reference for the TeensyROM CLI, the terminal client of the engine's API, built from `src/apps/cli`.

## When to Use This Skill

- Working on, running, testing, or packaging the CLI (`src/apps/cli`)
- Starting, restarting, or stopping the engine through the CLI, or working out why an engine did or did not start
- Questions about the `~/.teensyrom` home, `TEENSYROM_DATA_DIR`, or which files the CLI and the engine write
- Regenerating or reading the CLI's API client
- Following device logs from a CLI listener through the log hub

**Not for**: engine internals (use `backend-architecture`); building a release (use `release` or `release-local`).

## Overview

- **One tool, one version**: the CLI ships with the engine and the web app as one package, and the engine and the CLI share `<Version>` in `src/apps/Version.props`.
- **Client of the API only**: the CLI calls the engine's HTTP API and its log hub. It never references an engine project.
- **Single file**: a release `trom` is one self-contained single-file executable with embedded symbols and no companion files (ReadyToRun and native self-extract except on `osx-*`). The settings are a publish-only group in `TeensyRom.Cli.csproj`, active when a RID and `SelfContained=true` are both set, so builds and tests are unaffected. Never read files beside the assembly: `Assembly.Location` is empty in a single file, so the logo font (`Fonts/Chunky.flf`) is an embedded resource (`FontConstants.Logo`, falling back to `FigletFont.Default`).
- **Grammar**: `trom <noun> <verb>`, with the nouns `device`, `file`, `index`, `settings`, `engine` (alias `api`), `chipsynth`, `path`, `theme`, `watch-folder` and `transfer`, plus the top-level `init` (an agent's orientation report), `ui` (open Trom UI), `update` (update the suite) and `wait <duration>` (a cross-platform timer). `trom api start|status|stop` is `trom engine start|status|stop`; user docs teach `api`. `trom` alone opens the TUI. Every command takes `--json`; results go to stdout and diagnostics to stderr; exit codes are 0–6; no command prompts outside a terminal; `-` reads paths from stdin.
- **Orientation**: `trom init` starts (or replaces) the engine like any engine command, then reports versions, engine, web UI, devices, storage and index state, `update`, commands and problems; it changes nothing. A failed engine start is a problem in the report, and only then does it exit 3. When the engine runs but does not serve the web UI, `problems` says why: for a source engine whose `wwwroot` (under the API project) has no `index.html`, the front end was never built, so run `pnpm run build:frontend` from `src/`, then `trom api stop` and `trom api start`. `capabilities` lists every `noun verb` (for example `engine start`) and every top-level command (`init`, `ui`, `update`, `wait`); the `api` alias is not listed separately. `update` is `{installed, latest, available, installKind, checkedAt}`, where `installKind` is `release`, `homebrew`, `source` or `unknown`; it reads the release check's cache or refreshes it (3 s budget) and makes no network call for a source install.
- **Open Trom UI**: `trom ui` starts the engine if needed, opens `http://localhost:10213` in the browser and prints that address, the LAN addresses other devices reach, and the `https` address beside each one (text label "Secure, for MIDI and video"). The secure list is `secureNetworkAddresses` and is empty unless the engine's HTTPS is listening; it is built in `UiLauncher` from `GET /api/engine/https` (`--json`: `address`, `networkAddresses`, `secureNetworkAddresses`, `available`, `opened`, `https`, `problem`, `openFailure`). `--no-open` only reports. Openers: Windows shell-execute, macOS `open`, Linux `xdg-open`, WSL `wslview` then `xdg-open`. A browser that won't open is a notice ("open the address yourself") and exit 0; an engine that doesn't serve the web UI exits 1 with the diagnosis. The guided menu's "Open Trom UI" entry runs the same launcher.
- **HTTPS status**: the engine serves `GET /api/engine/https` (`GetHttpsStatus`; port 10214 from `Https:Port`). `EngineProbe.GetHttpsAsync` maps it to `EngineHttps` (`Engine/EngineOutcomes.cs`) and returns null for an older engine's 404 or any failure. `EngineStatus.Https` carries it, so `engine status`, `engine start`, `init` and `ui` all have it. Its `--json` is camelCase: `port`, `listening`, `problem`, `names`, `issuedAt`, `expiresAt`, `change` (`none`, `created`, `reissued`), `changeReason` (`unreadable`, `expiring`, `hostNameChanged`, `newAddress`) and `notice`. The endpoint's own enum values are PascalCase (`Created`, `Reissued`), so keep the two casings separate. Text output shows "Secure address" (`https://localhost:{port}`, or "not available" with the problem) and "Certificate expires" (`yyyy-MM-dd`). `HttpsNotice.For` (`Engine/HttpsNotice.cs`) writes the notice, and only when this run created or re-issued the certificate; `engine start`, `engine status`, `init` and `ui` print it.
- **Update**: `trom update` (`--check`, `-y|--yes`) needs neither an engine nor a device. A release install is replaced in place, a Homebrew install runs `brew upgrade`, and a source or unknown install is refused without a prompt (`--check` there says to use git, or gives the download link). `--check --json` writes `{installed, latest?, available, installKind, checkedAt?}` and exits 0 whenever the lookup worked. An install attempt writes those five fields describing the state after the update, plus `updated`; when `updated` is true also `from`, `to`, `engineWasRunning`, `engineRestarted` and `restartProblem?`. Nothing newer: `updated:false`, exit 0. Without `--yes` it asks to confirm; declined is exit 1 ("Cancelled; nothing was changed."), no terminal and no `--yes` is exit 2. Ctrl+C is "Cancelled." exit 1, but once the package is staged it no longer stops the stop and swap. If Trom API doesn't start again after a good update it still exits 0, with `engineRestarted:false`, `restartProblem` and a stderr notice (code `engineNotRestarted`, fix `trom api start`). The mechanism (verified download, staged package, journaled swap with rollback, restart through the new `trom`) is in the `distribution` skill. Code is under `Update/` (`UpdateRunner`, `ReleaseClient`, `PackageSwapper`, `ReleaseCheck`, `UpdateNotifier`); the commands are `Commands/Update/UpdateCommand.cs` (with `UpdateWork`, shared with the menu flow `Commands/Main/UpdateFlowCommand.cs`).
- **Update details worth knowing**: the swap targets the install's CLI folder, and `ApplyAsync` first runs `Recover` on any earlier half-finished update. Tar entries that are links or devices are refused. `PlatformRid.Current` comes from `RuntimeInformation.ProcessArchitecture`. The Homebrew path starts Trom API again through `<prefix>/bin/trom` even when brew fails. `TeensySettings` gained the bool `UpdateCheck` (default true): tests built with AutoFixture can flip any settable bool, so set values explicitly.
- **Release check**: at most daily, `trom` fetches the release list and caches `{checkedAt, latest, latestStable, attemptedAt, notifiedAt}` in `<home>/cli/release-check.json` (a failure retries after an hour; `attemptedAt` is written before the lookup and cleared by a success). One-shot interactive commands print a one-line stderr notice (code `updateAvailable`, fix `trom update`, at most once per 24 h; the lookup has 5 s and the end of the command waits at most 1 s) and the menu shows a line under the logo plus an "Update to {latest}" entry before Leave, which closes the menu after a successful update. Nothing prints under `--json`, for `--help`, `--version`/`-v`, a first word of `init` or `update`, or without a terminal. The `update-check` setting (`trom settings set update-check false`, default true) turns it off, and source and unknown installs never check. The hidden `TROM_RELEASES_URL` env var points the feed elsewhere (plain `http` allowed only through it); the default is the GitHub releases API of `MetalHexx/TeensyROM-Suite`. Tests and local trials use it with `.github/scripts/fake_release_feed.py`.
- **Wait**: `trom wait <DURATION>` accepts `45s`, `3m`, `3m20s`, `1h2m3s` (case-insensitive) and clock strings, where `3:20` is minutes:seconds and `00:03:20` hours:minutes:seconds, optionally with fractional seconds (`00:03:20.5000000`). The range is 1 second to 6 hours; anything else exits 2. It never starts the engine; Ctrl+C exits 1; `--json` writes `{"waited":"00:03:20"}`, otherwise stdout stays empty.
- **Full file records**: `file launch` and `file random` write the engine's full file record in their JSON; `file search` and `file ls` stay compact (and include `playLength`) unless given `--full`. Fields the engine leaves null are omitted (for example `avgRating` for an unrated file), and `title`/`creator` in the full record are the engine's values, which for games, images and firmware can differ from the compact form's labels.
- **Stderr under `--json`**: stderr may end with one compact JSON object, either the error `{"error":{"code","exitCode","message","details"?}}` (`code` is `failed`, `usage`, `engineUnavailable`, `noDevice`, `notFound` or `deviceBusy`) or a notice `{"notice":{"code","message","device","deviceId","storage","fix"}}`. `details` (`path`, `device`, `attempts`, `possibleCauses`) is present only for errors that have one, such as a directory that was not found after three reads. A notice's `device`, `deviceId`, `storage` and `fix` are optional and omitted when null (the update notices carry `code`, `message` and `fix`: `updateAvailable` fix `trom update`, `engineNotRestarted` fix `trom api start`). Stdout stays the bare result.
- **Index notice**: `file search` and `file random` read only what the engine has cached until a full index exists. On a storage whose index is incomplete they add a one-line notice on stderr (code `indexIncomplete`) naming the device, the storage and the exact `trom index build --device <name> --storage <sd|usb>` command; exit code and stdout are unchanged, and a fully indexed storage gets no notice. `device list` (and `--json`) reports this per storage as `sdIndexed` and `usbIndexed`, taken from the engine's `indexExists`.
- **Firmware version**: `init`, `device list`, `device discover`, `device reconnect` and `device rename` report each device's `firmwareVersion` in `--json`, exactly as the engine's `fwVersion` carries it, and their terminal output shows it too. Read it as text, not as a number: a tagged build reads `0.9-pr65`, a build from a dirty tree ends in `*` (`0.9-pr65*`), a release build is just the number, and it is empty when the version isn't known.
- **Directory reads**: `file ls` and the parent lookup behind `file launch`, `favorite` and `unfavorite` retry a failed directory read (the engine answers 404) up to two more times, because a stale device link fails the first reads and heals on a later one. A directory that still fails exits 5 with "not found, or the device did not answer".
- **Engine lifecycle**: a packaged CLI starts the engine from `<cli folder>/../api/TeensyRom.Api[.exe]` (`EngineLocator` reports mode Packaged and engine folder `<root>/api`, which is also the engine's working directory and content root); from source, the CLI builds the engine and starts it. A running engine whose version or build differs from the CLI's is restarted, except that a packaged CLI never replaces a running engine that is newer than itself: it fails with "TeensyROM Suite was updated while this trom was open — start trom again." (the guard for menus left open across an update). `trom api start` (or `engine start`) starts the engine, or reports it running, and exits 3 when it can't start; `trom api stop` shuts it down. Only one engine runs per home (the lock is `<home>/api/engine.lock`), and the engine keeps running after the CLI exits until it is stopped.
- **Device-free commands**: `chipsynth`, `settings`, `path`, `wait`, `update`, `engine status`, `engine stop`, and the help and version flags (`-h`/`--help`, `-v`/`--version`) run without starting an engine.
- **Home**: the CLI keeps its state in `~/.teensyrom/cli` and the engine keeps its in `~/.teensyrom/api`. `TEENSYROM_DATA_DIR` moves the whole home; set it to a temp folder whenever you run the CLI by hand during development.
- **Source runs**: from source, the CLI rebuilds and restarts the engine when the engine's sources have changed, recording the sources it built from in `<home>/cli/source-engine.json`. A source-mode engine is built and run as Release (`bin/Release`) so an install from source runs what a user should; developers get Debug by setting `TROM_ENGINE_CONFIGURATION=Debug` (any other value means Release). The recorded sources include the configuration, so a checkout that only has a Debug build rebuilds and restarts into Release on the next engine command, and switching the variable switches the engine the same way. The CLI passes the engine `--webroot` pointing at the API project's `wwwroot`, and it serves the built front end from there. The source fingerprint covers only the API and `Version.props`, so after a CLI-only change stop the engine (or use a fresh `TEENSYROM_DATA_DIR`) to relaunch it.
- **Windows file locks**: on Windows a running engine locks the DLLs in its `bin/Release` folder (`bin/Debug` when `TROM_ENGINE_CONFIGURATION=Debug`). Stop it with `trom api stop` (from source, run `dotnet run --project apps/cli/src/TeensyRom.Cli -- api stop` in `src/`) before you build the engine yourself, for example for engine tests or `generate-api-client.ps1`.
- **Non-interactive shells**: without a terminal, a direct command runs and exits instead of showing the menu.
- **Log following**: a listener calls the log hub's `Subscribe` and `Unsubscribe` on `/api/logHub`, and lines arrive as `LogProduced`.
- **Transfer lines**: while the TUI menu is open it follows `/api/transferHub`: `SubscribeAll` joins `transfers-all` and returns every job, and each change arrives as `JobSnapshot`. The hub client (`TransferLineStream`) starts in the background when the menu opens, seeds running jobs without a start line, and prints one start and one end line per job, worded like the web app's alerts (`TransferLines`). It never starts an engine; after the first flow readies one it starts again. One-shot commands never start it.
- **File verbs**: `file upload` and `file download` copy between this computer and the TeensyROM; `file upload --launch` asks the engine to launch the one file once it lands. With the auto-launch setting on, every upload launches one file the same way; the engine ranks the transferred files (games first, `.trh` never). `file next` and `file previous` step through the folder, search or shuffle the last launch came from; `file pause` and `file stop` control playback. `file banned` and `file unban` list and lift bans and take no `--device`, since bans are engine-wide.
- **Watch folders and transfers**: `watch-folder add|set|remove|pause|resume|list` manage the folders whose arriving files are sent to a TeensyROM, and `transfer list` shows every transfer, watch-folder ones included. Their `--json` is camelCase: `watch-folder list` is an array of `{id, path, enabled, state, destinations[]}`, each destination carrying `deviceId`, `deviceName`, `storage`, `path` and `launch`; `transfer list` carries `from.kind` (`upload` or `watchFolder`) and `launch.state`. The TUI's Watch Folders screen manages the same folders through the engine's `/api/watch-folders` endpoints.
- **Themes**: `theme list|show|apply|save|delete` tune the C64's menu colors through the engine's `/api/themes` and `/api/devices/{id}/theme`, via `IThemeService`, which the TUI's Theme screen also uses. `--json` colors are `{index, name}` keyed by the slot flags (`background`, `border`, `banner`, `time`, `keys`, `sources`, `names`); apply reports per device with `status` `applied|busy|failed` and exits 0, 6 (only busy) or 1.
- **Copy conventions**: `--to` names the destination, the device folder for upload and the local folder for download. Download defaults to the current folder. Upload with no paths sends the current folder's contents, and asks first unless `--yes` (the guard). A copy replaces a same-named file at the destination. An upload's first admitted file resets the device unless the engine believes it is idle with nothing launched on it, and a reset stops playback. Upload requires `--to`.
  - **Upload types**: a folder upload sends only the types the web app takes: `.sid`, `.crt`, `.prg`, `.p00`, `.hex`, `.kla`, `.koa`, `.art`, `.aas`, `.hpi`, `.seq`, `.txt`, `.d64`, `.nfo`, `.md`, `.ocp`, `.pic`, `.d71`, `.d81`, `.reu`, `.trh`, `.zip`, `.7z`, `.rar`, matched case-insensitively. Links are never followed; hidden and system entries are skipped without being counted.
  - **Left out**: a named file of another type is a failed row ("not a file type the TeensyROM takes"). When an upload leaves walked files out for their type, stderr gets a notice with the count, in every output mode; stdout and the JSON document don't carry it.
  - **Clean run**: a run that copies files and fails none ends with `Copied N files.` on stderr, outside `--json`.
  - **Empty download**: a device folder with nothing in it is created locally. A run with nothing to save exits 5 ("nothing to download").
  - **`localPath`** (download): a full path under the target, empty only for a path that was never classified (its parent listing failed, or it was not found).
  - **`totals.copied`**: counts the files an archive expands to, while `files` holds one row for the archive, so `copied + failed` can exceed the number of rows.
- **Last launch and the player**: each TeensyROM's last launch is kept in `<home>/cli/last-launch.json`. The player restores its state from that file and writes every change through, so `next`, `previous`, `pause`, `stop` and `wait --device` carry on across processes. The record keeps the newest 1000 random picks, the same bound as the web app's player history. A record with a missing path reads as unusable, the same as no record.
- **Wait and pause**: `wait --device <name>` holds the countdown while that TeensyROM's song is paused through trom, reading the last-launch record. Pauses made in the web app aren't seen.
- **Index build**: `index build` indexes every available storage, or the one `--storage` names. `index build --all` indexes every storage on every connected TeensyROM.
- **Engine logs**: `engine status --json` reports `logFolder` and `logFile`, the folder the engine writes to and its newest log file. `logFile` is absent unless an engine answers and has written one.
- **Hand-written client code**: `Api/TeensyRomApiClient.Upload.cs` is a hand-written partial of the API client, next to the generated `Api/Generated/`. Regeneration never touches it.
- **Rate limits**: only full scans of `/api/devices` (device discovery) are rate limited, to one per 5 seconds; a request over the limit is answered 503. A plain listing is never limited.

## Routing

Paths are relative to `src/` unless noted.

| Task | Where to go |
|------|-------------|
| CLI code: commands, engine lifecycle, services | `apps/cli/src/TeensyRom.Cli` (commands under `Commands/`, engine lifecycle under `Engine/`, home rules in `Common/TeensyRomHome.cs`) |
| API client | Regenerate with `pnpm run generate:cli-api-client` (runs `apps/cli/scripts/generate-api-client.ps1`). Never hand-edit `apps/cli/src/TeensyRom.Cli/Api/Generated/`. |
| Build and tests | `dotnet build apps/cli/TeensyRom.Cli.sln`; unit tests `dotnet test apps/cli/src/TeensyRom.Cli.Tests`; real-engine suite `dotnet test apps/cli/src/TeensyRom.Cli.Tests.Integration --filter "Category!=Hardware"`. The real-engine suite drives an engine through its `TestEngine` helper. `Category=Hardware` marks bench-only scenarios that need a TeensyROM attached. CI runs these in the repo-root `.github/workflows/pr-cli-checks.yml`. |
| Update code | `apps/cli/src/TeensyRom.Cli/Update/` (release feed, verified download, staging, swap, check cache), `Commands/Update/`, `Commands/Main/UpdateFlowCommand.cs`; tests in `TeensyRom.Cli.Tests` (`Update*`, `ReleaseCheck*`, `PackageSwap*` and friends) |
| Trom UI launcher | `apps/cli/src/TeensyRom.Cli/WebUi/` (`UiLauncher`, `BrowserOpener`, `LanAddresses`), `Commands/Ui/UiCommand.cs` |
| Engine HTTPS status and certificate notice (`GET /api/engine/https`) | CLI: `apps/cli/src/TeensyRom.Cli/Engine/` (`EngineProbe.GetHttpsAsync`, `EngineOutcomes.cs`, `HttpsNotice.cs`). Engine: `apps/api/src/TeensyRom.Api/Https/` (`HttpsStartup`, `HttpsCertificateStore`) and `Endpoints/Engine/GetHttpsStatus/` |
| Packaging the CLI | `distribution` skill (package layout, `trom update`, Homebrew formula); `release` for an official release, `release-local` for a local test build and a fake-feed update trial |
| Engine endpoints and hubs | `backend-architecture`; live debugging of a running engine against hardware: `api-live-debug` |
| Adding a reference file to this skill | `make-skill-template` |
